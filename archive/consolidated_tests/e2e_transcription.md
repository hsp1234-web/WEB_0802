# 抽象化摘要：端對端轉錄流程測試

本文檔旨在封存與總結專案中發現的三種針對「音訊轉錄」這一核心功能的端對端（E2E）測試。這三種測試代表了測試策略在不同開發階段的演進，從重型、完全整合的測試到輕量、解耦的現代測試。

---

## 設計演進分析

### 方法一：重型同步客戶端測試 (最早期，最笨重)

-   **來源**: `CL_0805/MP3_Converter_TXT/tests/test_full_system_flow.py`
-   **設計思路**:
    -   使用 `httpx.Client` (同步) 來呼叫 API。
    -   測試設定極為複雜，需要透過 `pytest` 的 fixture 同時啟動：
        1.  一個真實的 `live_api_server` (線上 API 伺服器)。
        2.  一個真實的 `live_worker` (背景轉錄任務處理程序)。
        3.  一個到 `db_connection` (資料庫) 的直接連線。
    -   測試流程會上傳一個真實的音訊檔案，並輪詢狀態，直到背景 worker 將任務處理完畢，狀態變為 `completed`。
    -   最後甚至會斷言轉錄出的文字內容是否正確。
-   **優點**:
    -   **最真實**: 這是最接近使用者實際操作的測試，覆蓋了從 API、訊息佇列、背景任務到資料庫的完整鏈路。
-   **缺點**:
    -   **極度緩慢**: 啟動真實的伺服器和 worker 非常耗時。
    -   **高度不穩定 (Flaky)**: 測試的成敗依賴於多個獨立進程之間的複雜互動（網路、進程調度、時序問題），很容易在沒有任何程式碼變更的情況下失敗。
    -   **設定複雜**: 在本地或 CI/CD 環境中可靠地設定這種測試是一項重大挑戰。

### 方法二：輕量級異步客戶端測試 (中期過渡)

-   **來源**: `CL_0805/MP3_Converter_TXT/tests/test_e2e_flow.py`
-   **設計思路**:
    -   同樣依賴 `live_api_server`，但不再啟動背景 worker。
    -   使用 `httpx.AsyncClient` (異步) 來呼叫 API。
    -   由於沒有 worker，此測試的目標是驗證 API 是否能成功接收任務並將其狀態設定為 `pending`。
-   **優點**:
    -   比方法一略快且穩定，因為它移除了對 worker 的依賴。
-   **缺點**:
    -   **測試覆蓋不完整**: 無法驗證任務是否能被成功處理。
    -   **目標不純粹**: 它仍然依賴一個真實的伺服器進程，使其比真正的 API 層級測試更重。

### 方法三：現代 FastAPI TestClient 測試 (現行標準，推薦)

-   **來源**: `tests/e2e/test_full_system_flow.py`
-   **設計思路**:
    -   **放棄真實伺服器**: 完全不啟動任何獨立的伺服器或 worker 進程。
    -   **使用 `TestClient`**: 利用 FastAPI 提供的 `TestClient`，它會在測試程序內部直接呼叫 app 的 ASGI 接口。
    -   **專注於 API 合約**: 測試的核心是驗證 API 的請求和回應是否符合預期。它驗證：
        1.  檔案上傳後是否能收到 `202 Accepted` 和一個 `task_id`。
        2.  使用該 `task_id` 是否能查詢到狀態。
        3.  其他相關的 API 端點（如 `/monitor`）是否正常工作。
        4.  API 是否能優雅地處理錯誤（如無效的 task_id）。
-   **優點**:
    -   **極速**: 執行速度非常快，因為沒有網路開銷和進程啟動延遲。
    -   **極度可靠**: 測試在單一進程中同步運行，消除了所有不穩定因素。
    -   **易於除錯**: 可以在測試中直接設定斷點來除錯 API 程式碼。
    -   **職責分離**: 它完美地實踐了測試金字塔的理念。這個 E2E 測試專注於驗證 API 層，而對 worker 的測試應該由更低層級的整合測試或單元測試來覆蓋。

---

## 結論與未來方向

從這三種測試的演進中，我們可以看到一個清晰的趨勢：**從笨重、緩慢、不穩定的完全整合測試，轉向更輕量、更快速、更可靠、職責更單一的測試。**

-   **方法一** 的理念（測試真實的完整流程）是好的，但它更適合被歸類為**系統測試**或**冒煙測試**，應該在一個獨立的、部署後的環境中，以非常低的頻率運行（例如每天一次），而不是作為開發過程中的一部分。
-   **方法二** 是一個不成功的過渡，它既沒有方法一的真實性，也沒有方法三的輕便性。
-   **方法三** 是 API 層級端對端測試的**黃金標準**。它應該在每次提交程式碼時都在 CI/CD 流程中運行。

因此，我們決定：
1.  **保留 `tests/e2e/test_full_system_flow.py`** 作為主要的 API E2E 測試。
2.  將另外兩個舊的 E2E 測試**封存並刪除**，它們的設計思路已在此文件中記錄。

# 抽象化摘要：整合測試的類型與演進

本文檔旨在分析和歸類專案中存在的兩種核心的「整合測試」類型，並記錄為了使專案結構更清晰而進行的重組活動。

---

## 整合測試的兩種模式

在探查過程中，我們發現了兩種目的和方法都截然不同的整合測試。了解它們的區別對於維護和擴展測試套件至關重要。

### 模式一：服務層級整合測試 (System/Service Integration)

-   **代表檔案**: `tests/integration/test_prometheus_pipeline_flow.py`
-   **核心思想**: 測試多個獨立運行的「服務」之間是否能正確協同工作。這是一種**黑箱測試**。
-   **執行方式**:
    1.  在背景中啟動一個或多個真實的服務進程（例如 FastAPI 伺服器、背景任務 Worker）。
    2.  測試腳本作為一個「客戶端」，透過網路協議（如 HTTP）向這些服務發送請求。
    3.  斷言服務的最終「副作用」是否符合預期（例如，資料庫中出現了新紀錄、檔案系統中創建了檔案）。
-   **優點**:
    -   **高保真度**: 非常貼近真實世界的使用場景。
    -   **覆蓋廣泛**: 一個測試可以驗證從 API 端點到底層任務處理的整個鏈路。
-   **缺點**:
    -   **複雜且慢**: 需要管理服務進程的啟動和關閉。
    -   **不穩定 (Flaky)**: 容易受到時序問題、端口衝突等環境因素的影響。

### 模式二：類別庫層級整合測試 (Library/Class Integration)

-   **代表檔案**: `tests/integration/test_data_pipeline_library.py` (原位於 `CL_0805/...`)
-   **核心思想**: 在單一的測試進程中，驗證多個類別或模組之間是否能正確地交互。這是一種**白箱測試**。
-   **執行方式**:
    1.  直接在測試腳本中 `import` 需要測試的類別（例如 `DataPipeline`, `TimeAggregatorStep`）。
    2.  實例化這些類別。
    3.  直接調用它們的方法（例如 `pipeline.run()`）。
    4.  斷言方法是否返回了預期的結果，或者是否在沒有拋出異常的情況下成功執行。
-   **優點**:
    -   **快速且可靠**: 沒有網路或多進程的開銷，執行穩定。
    -   **易於除錯**: 可以在程式碼中直接設置斷點。
-   **缺點**:
    -   **覆蓋面較窄**: 無法驗證服務配置、網路通信等問題。

## 結構重組決策

**觀察**:
在重構之前，這兩種測試被分散在不同的目錄下，特別是類別庫層級的測試被深埋在一個舊的專案結構 (`CL_0805/`) 中，這使得開發者難以全面了解專案的整合測試策略。

**行動**:
為了統一和簡化專案結構，我們執行了以下操作：
1.  **移動並重命名**: 將 `CL_0805/0709_wolf_88/tests/integration/pipelines/test_data_pipeline.py` 移動到了 `tests/integration/`。
2.  **明確化**: 將其重命名為 `test_data_pipeline_library.py`，以便從檔名就能清晰地看出其測試目標是「類別庫」而非「服務」。

**結果**:
現在，所有整合測試都集中在 `tests/integration/` 目錄下，開發者可以輕易地找到並區分這兩種不同但都很有價值的整合測試類型。
